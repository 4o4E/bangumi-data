# 架构方案反选表（已完成首轮决策）

当前接受：`SCOPE-A + SOURCE-A + PROCESS-B + DB-A + IMPORT-A + API-A + CLIENT-A + SEARCH-A + POP-A + HISTORY-B + IMAGE-A + AUTH-A（环境变量单 token） + RELEASE-A（镜像改为 GHCR）`。

具体解释以 `docs/decisions` 下状态为“已接受”的 ADR 为准。未被当前决策覆盖的候选仍保留，供未来重新评估。

下列每一项可以独立反选。标记“推荐”的组合是一条可直接实施的首版路径，不代表已经决定。回复时可以只写变更项，例如：`DB-C、API-B、SEARCH-B，其余默认`。

## 默认组合摘要

`SCOPE-A + SOURCE-A + PROCESS-B + DB-A + IMPORT-A + API-A + CLIENT-A + SEARCH-A + POP-A + HISTORY-B + IMAGE-A + AUTH-A + RELEASE-A`

## 1. 首版数据范围

| 编号 | 方案 | 优点 | 代价 |
| --- | --- | --- | --- |
| **SCOPE-A（推荐）** | 数据模型支持全部作品类型；首批导入动画、游戏、角色、人物和全部关系 | 不为 Wife 写死；先覆盖近期需求，未来扩类型不用改表和 API 主结构 | 首版接口要考虑暂未导入的类型 |
| SCOPE-B | 首版直接导入书籍、动画、音乐、游戏、三次元及全部实体 | 一次形成完整公共数据服务 | 导入、验证和存储规模最大，首版周期更长 |
| SCOPE-C | 只做动画/游戏及作品—角色关系 | 最快落地 | 很快会因为人物、声优或其他消费者再次改边界 |

## 2. 上游采集来源

| 编号 | 方案 | 优点 | 代价 |
| --- | --- | --- | --- |
| **SOURCE-A（推荐）** | Archive 周期全量基线 + v0 API 热数据/按需刷新 | 全量成本低、及时性可补、尊重官方服务压力 | 需要协调两种来源和冲突优先级 |
| SOURCE-B | 只用 Archive | 最简单、可重复导入 | 最多滞后一周，无法及时修正热点数据 |
| SOURCE-C | 只用 v0 API 遍历/搜索 | 数据可以更及时 | 搜索为实验接口；请求量、断点续跑和漏项风险高 |
| SOURCE-D | 部署官方 server 或其完整数据栈 | 最接近官方内部能力 | MySQL、Redis、Kafka、Meilisearch 对当前目标过重 |

推荐冲突规则：Archive 建立全量事实，API 中更新时间更晚的实体覆盖当前值；所有覆盖都保留来源时间和导入批次。

## 3. API 与采集进程关系

| 编号 | 方案 | 优点 | 代价 |
| --- | --- | --- | --- |
| **PROCESS-A（推荐）** | 同一镜像提供 `api`、`worker` 两个启动命令，部署成独立容器 | 代码和模型复用；API 可横向扩容；采集失败不拖垮查询 | Compose/Kubernetes 需要两个 service |
| PROCESS-B | API 进程内置调度器 | 部署单一 | 多实例会重复同步；同步占用 API 资源；故障域混合 |
| PROCESS-C | API + 纯一次性 CronJob 镜像 | worker 无常驻资源 | 手动按需刷新和队列消费要另建入口 |

## 4. 主数据库

| 编号 | 方案 | 优点 | 代价 |
| --- | --- | --- | --- |
| **DB-A（推荐）** | PostgreSQL 规范化实体/关系表 + 来源 JSONB staging | 适合多消费者、多实例、增量刷新、复杂关系与统计 | 运维成本高于单文件数据库 |
| DB-B | PostgreSQL 以来源 JSONB 为主 | 初期导入快、抗字段变化 | 查询契约、索引和数据质量会越来越难维护 |
| DB-C | SQLite + 每周原子替换数据库文件 | 单机只读最简单，社区已有成功案例 | 多实例切换、增量写入、远程共享和高可用较弱 |

## 5. 全量导入原子性

| 编号 | 方案 | 优点 | 代价 |
| --- | --- | --- | --- |
| **IMPORT-A（推荐）** | PostgreSQL 代际数据：staging 导入、校验、事务切换 active generation、延迟清理旧代 | API 始终读完整版本；失败可回退；适合独立 worker | 查询需携带活动代或使用切换视图，存储短时翻倍 |
| IMPORT-B | 新建临时数据库，验证后切换连接目标 | 隔离最彻底 | 连接池和部署配置切换复杂，数据库管理权限要求高 |
| IMPORT-C | 在线原地 upsert/delete | 实现直观、空间小 | 长导入期间可读到混合版本，失败恢复最困难 |

## 6. 对外查询契约

| 编号 | 方案 | 优点 | 代价 |
| --- | --- | --- | --- |
| **API-A（推荐）** | `/api/v1` REST + OpenAPI，返回自有稳定 DTO | Ktor 易实现；缓存、调试、客户端发布都直接 | 复杂组合查询可能需要增加专用 endpoint |
| API-B | GraphQL | 消费者可精确取字段，关系查询灵活 | 缓存、复杂度限制和 Kotlin 客户端维护更复杂 |
| API-C | gRPC | 强类型、高吞吐、流式友好 | 浏览器与人工调试不便，对当前读服务收益有限 |
| API-D | REST 主接口 + GraphQL 高级查询 | 能同时覆盖简单和复杂消费者 | 首版维护两套契约，不建议过早引入 |

公共 API 应返回规范化领域模型，不直接透传 Bangumi v0 或 Archive JSON；原始记录只开放给管理/诊断接口。

## 7. Kotlin 消费客户端

| 编号 | 方案 | 优点 | 代价 |
| --- | --- | --- | --- |
| **CLIENT-A（推荐）** | 同仓库 `api-model` + 手写 Ktor `http-client`，发布 Maven | 与 mc-skin 模式一致；错误语义、重试和兼容性可人工控制 | API 新增时要同步维护客户端 |
| CLIENT-B | OpenAPI 自动生成 Kotlin 客户端 | 覆盖面容易与 API 同步 | 生成代码体积和可读性较差，运行时选型受生成器约束 |
| CLIENT-C | 只发布 OpenAPI，不发布客户端 | 服务端最省维护 | 每个消费者重复处理认证、错误、分页和兼容性 |

客户端版本只表达契约版本。Bot 固定依赖一个已发布版本，服务端保持 `/api/v1` 向后兼容，因此不要求两边同时部署。

## 8. 搜索能力

| 编号 | 方案 | 优点 | 代价 |
| --- | --- | --- | --- |
| **SEARCH-A（推荐）** | PostgreSQL `pg_trgm` + GIN/全文索引 | 不增加服务；足够支持中文名、原名、别名和模糊匹配首版 | 大规模相关性和拼写纠错弱于专用搜索引擎 |
| SEARCH-B | Meilisearch | 相关性、拼写容错和响应速度更强 | 新增索引同步、重建与运维组件 |
| SEARCH-C | 首版不提供搜索，只按 ID/过滤查询 | 最快、契约最小 | 其他服务很快会各自重复做搜索 |

## 9. 人气与“熟悉角色”派生

| 编号 | 方案 | 优点 | 代价 |
| --- | --- | --- | --- |
| **POP-A（推荐）** | 保存原始热度历史，并按作品计算版本化 rank、归一分数、快速跌落点和 `CORE/FAMILIAR/LONG_TAIL` 层级 | 通用于动漫和游戏；消费者选层级，不写死固定前 N% | 需要设计可解释算法与回归样本 |
| POP-B | 服务只保存原始收藏数，由每个消费者计算 | 数据服务边界最纯 | 算法重复、结果不一致，Bot 仍需理解完整作品角色分布 |
| POP-C | 直接输出 Wife 候选/权重 | Bot 最简单 | 把首个消费者规则耦合回通用服务，不建议 |

推荐派生只描述“在该作品内的相对熟悉度”，不直接决定 Wife 是否入池；角色的主角/配角/客串关系仍原样保留。快速跌落算法不能写死作品或固定比例，且每次结果带 `algorithmVersion`。

## 10. 历史与可追溯性

| 编号 | 方案 | 优点 | 代价 |
| --- | --- | --- | --- |
| **HISTORY-A（推荐）** | 当前实体 + 热度时间序列 + 导入批次/来源/校验摘要 | 能重算人气、解释变化和定位错误，存储可控 | 需要保留策略和归档任务 |
| HISTORY-B | 只保存当前状态和最后更新时间 | 最省空间 | 无法复现历史算法结果或判断热度变化 |
| HISTORY-C | 永久保存每次完整原始快照 | 审计最完整 | 存储增长快，大量重复数据 |

## 11. 图片处理

| 编号 | 方案 | 优点 | 代价 |
| --- | --- | --- | --- |
| **IMAGE-A（推荐）** | 数据库只存来源 URL、尺寸/哈希等元数据；消费者自行缓存 | 服务职责清晰，首版不承担流量代理 | 多消费者可能重复下载同图 |
| IMAGE-B | 后续增加独立对象存储和图片代理 | 统一缓存、可固定内容地址 | 带宽、版权/再分发与清理策略都要额外确认 |
| IMAGE-C | 图片二进制进入 PostgreSQL | 备份看似统一 | 数据库膨胀，不建议 |

## 12. 访问控制

| 编号 | 方案 | 优点 | 代价 |
| --- | --- | --- | --- |
| **AUTH-A（推荐）** | 读 API token 与管理/同步 token 分离，内网也校验 | 权限清晰，未来暴露给其他服务无需重构 | 部署要分发和轮换 secret |
| AUTH-B | 公开只读 API，管理端 token | 社区复用方便 | 需要限流、防滥用和明确数据再分发条件 |
| AUTH-C | 仅靠 Docker 网络隔离，不做应用认证 | 配置最少 | 一旦网络边界变化就失去保护，审计能力弱 |

## 13. 发布与部署

| 编号 | 方案 | 优点 | 代价 |
| --- | --- | --- | --- |
| **RELEASE-A（推荐）** | DockerHub 发布服务镜像；Nexus 发开发版客户端；稳定 tag 发 Maven Central | 与现有 Kotlin 项目习惯一致；服务与客户端各自版本化 | 需要维护两类发布流水线和签名凭证 |
| RELEASE-B | DockerHub + 客户端只发 Nexus | 首版设置快 | 外部消费者需要配置私有仓库 |
| RELEASE-C | 只发 Docker 镜像和 OpenAPI | 制品最少 | Kotlin 消费端缺少统一错误与模型实现 |

项目自身许可证仍需单独选择。官方 Archive 没有可识别 LICENSE，且参考服务包含 AGPL/GPL 项目；在许可证和数据再分发边界确认前，只提交原创实现和公开接口调用，不复制社区代码。

## 建议的首版模块形态（选择后才创建）

```text
bangumi-data/
├─ api-model/        # 稳定 DTO、分页、错误模型
├─ http-client/      # 面向 Kotlin 消费者的 Ktor 客户端
├─ domain/           # 与上游和存储无关的领域模型及派生算法
├─ storage-postgres/ # 表、查询和 migration
├─ source-archive/   # Archive 下载、校验和流式解析
├─ source-bangumi/   # v0 API、限流、缓存和按需刷新
└─ app/              # api/worker 两种启动命令和 Docker 入口
```

这只是 `SCOPE-A + SOURCE-A + PROCESS-A + DB-A + CLIENT-A` 的预览；反选完成前不创建空模块，避免目录结构反过来绑架决策。
